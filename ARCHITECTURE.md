# Architecture

Next.js server components load user-scoped data. Server actions validate external payloads with Zod, verify the Supabase user, and write through the public client using the user's cookie session. Supabase RLS is the final authorization boundary, including direct REST access. No service-role key or custom backend is used. OAuth callback exchanges PKCE codes and persists cookies. Protected loaders redirect unauthenticated users; public routes cover setup, login, callback, and errors.

Trips own independent segments and a hub-preferences record. Multiple destination periods and stays can overlap; there is no destination-to-hotel assumption. Segments have inclusive date ranges, optional local times, explicit IANA time zones, and independent idea/planned/confirmed states. Flexible ordering is explicit. Database triggers prevent out-of-trip ranges, including shortening an existing trip. RLS protects preferences and segments through ownership of their parent. Trip deletion cascades. UTC timestamps track changes; trip lifecycle uses trip-local dates.

Segment fields capture addresses, providers, confirmation references, transport modes, departure and arrival locations, local times and independent arrival time zones. Separate structured stay and transport details, destination relations, traveler records, and departure/arrival zones remain needed for richer booking workflows. No route or booking facts are inferred. Later phases should add dedicated typed detail tables, membership policy helpers, private storage policies and audit events through migrations. Sensitive documents must not be added to shared generic notes.

The Next.js request proxy refreshes Supabase sessions before server components load user data, preserving rotated cookies. No personal data is intentionally logged. No offline data is retained by a service worker.

Guided setup calls `create_trip_with_destinations` using invoker privileges. Trip creation and all submitted destinations are one database transaction; ownership comes from auth.uid(), never a client owner ID. Optional destination_id self-references are constrained to destination segments of the same trip. Destinations cannot have destination parents. Deleting a destination unlinks surviving plans; deleting the trip cascades all segments. Database checks reject unknown time zones even for direct REST/RPC writes.
